# ADR-0001: Альбом и Исполнитель — computed-агрегаты, не первокласные сущности (в v1.0.4)

**Status:** Accepted
**Date:** 2026-05-21
**Deciders:** Matvey Bakhmatov (продуктовый владелец и единственный разработчик)

> **Сноска 2026-10-15.** После пересмотра роадмапа минор «Metadata & Lyrics», который ниже упоминается как `1.3.0`, стал `1.4.0` (см. [roadmap-vision.md, раздел 13](../roadmap-vision.md#13-журнал-пересмотров)). Суть решения не меняется.

## Context

В итерации D (v1.0.4, эпик «Library 2.0») мы вводим UI-views «Альбомы» и «Исполнители» — пользователь должен видеть свою библиотеку, сгруппированную по альбому или исполнителю, и открывать детальные страницы (drill-down) внутри левой колонки.

Доменная модель `Track` (см. [`MusicBakh.Core/Domain/Track.cs`](../../MusicBakh.Core/Domain/Track.cs)) уже содержит строковые поля `Artist`, `Album`, `Genre`, `Year`-я в текущем виде НЕТ. История, теги, рейтинги, реакции, FTS-индекс, плейлисты — всё привязано через `Track.Id`. Никаких `Albums`/`Artists`-таблиц или FK сейчас нет.

Roadmap [`docs/roadmap-vision.md`](../roadmap-vision.md) явно планирует на `v1.3.0` («Metadata & Lyrics») провайдер-архитектуру для внешних источников: MusicBrainz, Discogs, Last.fm. Эти провайдеры выдают сущности «альбом» и «исполнитель» с метаданными (release year, label, biography), и именно в `1.3.0` появляется естественная потребность хранить эти данные отдельно от трека.

Силы:
- Хочется поскорее доставить рабочие views без потери качества.
- Хочется не делать сейчас работу, которую через 2-3 минора всё равно придётся переделывать (т.к. провайдер-сущности `1.3.0` могут изменить выбранную здесь схему).
- Не хочется добавлять YAGNI-абстракции.
- На сегодняшней библиотеке (50k треков) `GROUP BY` по SQLite — недорогая операция (миллисекунды).

## Decision

Принимаем **Option A**: Альбом и Исполнитель — это **производные группировки**, вычисляемые из существующих `Track.Artist` / `Track.Album` полей. Никаких новых таблиц, ни FK, ни импорт-flow не меняется.

- Альбом = `GROUP BY (Track.Artist, Track.Album)`.
- Исполнитель = `GROUP BY Track.Artist`.
- Обложка альбома = обложка первого трека в группе (по `Track.Id`).
- Сортировка треков внутри альбома: добавляется поле `Track.Year` (int?) + `Track.TrackNumber` (int?), оба читаются из ID3 при импорте.
- Сортировка альбомов: по умолчанию — по году убыванием (NULL Year идут последними), вторичный ключ — `Album.Title` ASC.
- Сортировка исполнителей: по числу треков убыванием, вторичный ключ — `Artist.Name` ASC.

Логика группировки живёт в новом `MusicLibrary.Services.Library.LibraryGroupingService` (или продолжение существующего `LibraryFilter`), который принимает `IReadOnlyList<Track>` и возвращает `IReadOnlyList<AlbumAggregate>` / `IReadOnlyList<ArtistAggregate>`. Тесты pure-функция, без БД.

## Options Considered

### Option A: Computed-агрегаты (выбрано)

| Dimension | Assessment |
|-----------|------------|
| Complexity | Low |
| Cost | ~2-3 дня скоупа доменной части (без UI) |
| Scalability | Хорошо для библиотек до 50–100k треков (GROUP BY + IN-memory агрегация) |
| Team familiarity | Высокая — паттерн `LibraryFilter` уже есть в `1.0.3` |

**Pros:**
- Никаких миграций схемы для агрегатов (только `AddTrackYear` + `AddTrackNumber` — две колонки + индексы).
- Существующие 213 тестов не ломаются.
- Новые треки сразу попадают в нужный альбом без resolve-логики.
- Полная совместимость с FTS, тегами, рейтингами, реакциями, историей — всё уже на `Track.Id`.
- Подходит для unit-тестов как pure-функция.

**Cons:**
- Альбом не может иметь собственных метаданных (release year, label, override-обложка) — всё привязано к трекам.
- Два трека с разным написанием тега `Album` («The Dark Side of the Moon» vs «Dark Side of the Moon») трактуются как разные альбомы — пользователь видит дубль.
- Когда в `1.3.0` появятся `IMetadataProvider`/`IArtistInfoProvider`, придётся реструктурировать модель и потенциально мигрировать данные.

### Option B: Первокласные сущности

| Dimension | Assessment |
|-----------|------------|
| Complexity | High |
| Cost | ~2-3 недели скоупа: новые домены/репозитории/миграция/изменения импорта/UI на FK |
| Scalability | Хорошо при любом размере (всё реляционно индексируется) |
| Team familiarity | Средняя — стиль EF Core знаком, но resolve-логика на импорте новая |

**Pros:**
- Чистая реляционная модель: альбом и исполнитель имеют идентичность, не зависящую от текстовых тегов.
- Решает проблему дублей «The Dark Side» vs «Dark Side» (если ввести fuzzy-matching) или хотя бы локализует её в одном месте (Album-резолвер).
- Готовая база для био из Last.fm, ручных правок (override-обложка, release year), smart playlists «все альбомы 2023 года».

**Cons:**
- Большая итерация: новые `Albums`/`Artists`-таблицы, FK `Track.AlbumId` / `Track.ArtistId`, изменения в `TrackImporter` (resolve-or-create на импорте), бэкфилл существующих треков в новые сущности через одноразовую миграцию.
- Resolve-логика на импорте: что делать с расхождениями написания, как объединять «Sabaton» и «sabaton», как разруливать compilations («Various Artists»). Нет правильного универсального ответа без UI ручного слияния.
- Все существующие биндинги в `MainViewModel`, `LibraryFilter`, FTS, history-replay завязаны на текстовые `Track.Artist`/`Track.Album` — придётся переписать почти все запросы и тесты.
- Велик риск того, что архитектура, выбранная здесь, окажется неоптимальной для `1.3.0` метадата-провайдеров, и её придётся переделывать второй раз.

### Option C: Computed + опциональная override-таблица

| Dimension | Assessment |
|-----------|------------|
| Complexity | Medium |
| Cost | ~1 неделя — computed-часть из A + новая `AlbumOverrides`-таблица + резолвер «overlay-pattern» |
| Scalability | Те же ограничения, что у A |
| Team familiarity | Средняя — overlay-pattern не использовался в проекте |

**Pros:**
- Гибкость: можно вручную исправить год/обложку конкретного альбома без миграции на FK.
- Не требует resolve-логики на импорте — overrides создаются юзером по требованию.

**Cons:**
- Концептуально лишний слой, который **сейчас не имеет ни одного потребителя** (нет UI ручных правок альбома — это `1.3.0`-задача).
- Overlay-pattern усложняет тесты: каждый запрос на «дай альбом X» должен учитывать наличие override.
- Классический YAGNI: вводится «на будущее», но к моменту реального использования (`1.3.0`) дизайн с большой вероятностью изменится.

## Trade-off Analysis

Главная ось — **сейчас или в `1.3.0`**:

- В `1.3.0` всё равно вводится `IMetadataProvider` / `IArtistInfoProvider`. Эти провайдеры будут поставлять album/artist-объекты с метаданными — и тогда естественно ввести их в Core как агрегаты с собственным жизненным циклом.
- К `1.3.0` у нас уже будет работающий computed-альбомный view (после `1.0.4`), мы поймём реальные шаблоны использования и сможем правильно спроектировать переход на first-class сущности.
- Введение first-class сущностей сейчас (`B`) — это работа «на ощупь», без понимания, какие именно метаданные нужны, как разруливать дубли, как поступать с compilations.
- `Option C` пытается захеджировать, но единственный реальный кейс для overrides — это **именно** тот случай, когда нужны first-class сущности (`B`). То есть `C` — это `A` + накладные расходы без реальной выгоды.

Ключевой риск выбора `A`: дубли альбомов из-за расхождений в написании тега. Митигация:
- Не делать ничего автоматически (молча мерджить ≠ хорошо для пользователя).
- В `1.3.0` ввести `AlbumDuplicateDetector` как часть метадата-флоу.
- В backlog `1.0.5–1.0.7` оставить «возможность вручную слить два альбома» как small feature, если пользователь начнёт жаловаться.

## Consequences

**Что становится проще:**
- Альбомный/исполнительский view ⇒ просто новый VM + `IGroupingService`-функция + новые UI-шаблоны.
- Импорт треков не меняется. FTS, теги, рейтинги, история не меняются.
- Тесты группировки — pure-функция, не требует БД.

**Что становится сложнее:**
- Когда в `1.3.0` будут вводиться first-class `Album`/`Artist`, придётся:
  - Завести `Albums`/`Artists` таблицы.
  - Миграция (одноразовая): отсканировать `Tracks` и создать соответствующие записи.
  - `Track.AlbumId` / `Track.ArtistId` FK + бэкфилл.
  - `LibraryGroupingService` рефакторится из «group existing tracks» в «query Albums table».
  - UI-биндинги (`AlbumDetailViewModel`, `ArtistDetailViewModel`) переходят с computed-агрегатов на сущности — но публичный интерфейс агрегатов остаётся, что снижает blast radius.
- Дубли альбомов («The Dark Side» vs «Dark Side») остаются видимыми до `1.3.0+` — это explicit cost.

**Что нужно пересмотреть:**
- При планировании `1.3.0` (минор «Metadata & Lyrics») — обязательно вернуться к этому ADR и оформить отдельный ADR-0002 о переходе на first-class сущности.
- Если пользователи (то есть мы сами) начнут регулярно жаловаться на дубли альбомов до `1.3.0` — приоритизировать ручное слияние альбомов как small feature.
