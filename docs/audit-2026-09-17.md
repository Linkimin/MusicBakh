# Технический и продуктовый аудит MusicBakh

Дата: 2026-09-17. Исходная ревизия: `b7c1e80`. Отчёт записан до изменения production-кода.

## A. Фактическое устройство и исходное состояние

MusicBakh — действующий локальный WPF-плеер, а не заготовка. Четыре production-проекта и один xUnit-проект; .NET 10, C# 14, EF Core SQLite, TagLibSharp, WPF MediaPlayer. Версия сборки 1.0.4, но в исходниках уже есть значительная часть итерации 1.0.5 (плейлисты). Рабочее дерево на старте чистое.

`App.OnStartup` создаёт Generic Host, регистрирует Infrastructure и Presentation, синхронно выполняет EF migrations → JSON migration → built-in seeding, затем разрешает и показывает MainWindow. MainWindow загружает настройки через репозиторий и присваивает свойства MainViewModel. Presentation действительно ссылается на Infrastructure; утверждение об отсутствии этой ссылки в architecture.md неверно.

MainViewModel владеет полной библиотекой, отображаемой коллекцией, кэшем тегов, фильтрами, агрегатами альбомов/исполнителей, стеком навигации, выбранным и играющим треком, очередью и таймером прогресса. PlaylistsViewModel владеет CRUD плейлистов и уведомляет об изменениях содержимого. Track immutable (init-only); репозитории возвращают новые экземпляры. Это делает синхронизацию по identity особенно важной.

Поиск: задержка WPF Binding 250 ms → SearchText → ApplyFilters → SqliteFtsSearchService → параметризованный MATCH + bm25 + LIMIT → LibraryFilter → DisplayedTracks → группировки. LibraryFilter уже восстанавливает порядок search hits и канонические объекты библиотеки. External-content FTS5 поддерживается INSERT/UPDATE/DELETE-триггерами. Миграционные тесты используют реальную SQLite; другие repository-тесты используют EnsureCreated и не проверяют триггеры.

Воспроизведение: команды VM → MediaPlayerAudioService; новый MediaPlayer при Open, отсечение событий предыдущего экземпляра, MediaOpened подтверждает запись истории. Auto-next использует стратегии Off/Current/Library. Очередь — снимок списка, но позиция вычисляется по ID трека. UI выбирает NowPlayingTrack = PlayingTrack ?? SelectedTrack, а часть управляющих команд и редактирование рейтинга зависят от SelectedTrack.

Импорт: модальный AddTrackWindow → AddTrackViewModel → TrackImporter копирует/скачивает файл в пользовательский Music → TagLib → MusicBrainz/iTunes для недостающих данных → embedded/iTunes/procedural cover → кандидат → подтверждение → SQLite Add. Файлы создаются раньше подтверждения и записи БД. URL ограничен 50 MiB, но чтение тела ответа не имеет отдельного дедлайна. Отмена окна не отменяет операцию.

Данные: `%LocalAppData%/MusicLibrary/library.db`, Music и Covers; встроенные ресурсы рядом с exe. Контекст EF короткоживущий на операцию; история и связи удаляются каскадно. JSON legacy после переноса переименовывается в backup. Настройки — KeyValueStore. Инсталлятор Inno Setup сохраняет пользовательский каталог при удалении. CI Windows собирает Release и запускает тесты. Телеметрии/облака/Supabase нет. Локального постоянного журнала ошибок и обработки ошибки старта нет.

Baseline (Windows, SDK 10.0.201):

- `dotnet build MusicLibrary.sln --nologo`: успешно, 0 предупреждений, 0 ошибок, 52 s включая restore.
- Обычный набор: 278/278, 5.26 s вместе с test runner.
- Отдельный benchmark 50k: 1/1, 18.73 s вместе с подготовкой/runner; утверждение среднего поиска <100 ms выполнено.
- Повторный полный набор: 279/279, длительность тестов 14 s. TRX: `TestResults/baseline-all/baseline-all.trx` (ignored).
- Первый общий запуск пришлось прервать после нескольких минут без результата; зависание повторно не воспроизвелось. Не считать доказанной ошибкой конкретного теста.
- Native playback/аудиоустройство, визуальная проверка DPI и установленного приложения пока не проверены; зелёные mock-тесты их не заменяют.

## C. Архитектурные решения

- **Must change:** ownership позиции очереди и импортных файлов; пересчёт состояния; защищённая миграция и обработка I/O.
- **Should change:** пакетная загрузка тегов, общий internal Track mapper, узкие методы обновления представлений, постоянный транспорт.
- **Optional:** дальнейшее выделение PlaybackViewModel, async загрузка всей библиотеки после измерений, виртуализированная сетка альбомов.
- **Leave as-is:** WPF, EF/SQLite/FTS5, четыре проекта, DI, snapshot-очередь, immutable Track, локальная модель хранения, built-in seed и существующие функции. Ни backend, ни новый UI framework, ни event bus не нужны.

## D. Целевой UX

Сохранить тёмную палитру с тёплым акцентом. Библиотека — основной рабочий экран; все четыре режима и поиск доступны постоянно. Транспорт — закреплён снизу и управляет текущим воспроизведением независимо от выделения. Редактор выбранного трека подписан отдельно. Ошибка импорта/поиска/сохранения должна объяснять действие пользователя, не сообщать ложный успех. Проверять минимальный размер, длинные названия, пустую выдачу и управление клавиатурой.

## E. План небольших срезов

Каждый срез: регрессионный тест → подтверждённое падение → минимальное исправление → build + соответствующие тесты. Финал: полный Release build/test, benchmark отдельно, publish и визуальный smoke. Существующие пользовательские файлы не используются как тестовые данные.

- [x] 1. D01–D04: migration/settings/connection string. Файлы Infrastructure/Migration, Persistence, тесты Migration и Persistence. Повреждённый JSON остаётся на месте; дубли путей переносятся один раз; NaN/Infinity/enum безопасны.
- [x] 2. P01–P02: очередь и транспорт. MainViewModel + MainViewModelTests/NavigationTests. A,A,B проходит обе позиции, pause/resume сохраняет очередь, сброс выбора не блокирует pause.
- [x] 3. S01–S03: ограниченный безопасный запрос, корректные разделители, отсутствие потери совпадений при фильтрах. FtsQueryBuilder, ApplyFilters, реальные FTS-тесты и VM с >500 результатами.
- [x] 4. L01–L02/F01: мутации и теги. ITagRepository/SqliteTagRepository, MainViewModel, тесты реальных связей и обновления агрегатов. Одна пакетная загрузка, фильтрация без SQL на каждый трек.
- [x] 5. I01–I02: жизненный цикл импорта. TrackImporter/AddTrackViewModel/AddTrackWindow, cancellation/failure tests с временными каталогами и fake HTTP.
- [x] 6. E01–E02/D03: ошибки и startup recovery. Обработка ожидаемых storage errors, локальная диагностика, резервная копия перед миграциями; никаких автоматических destructive reset.
- [x] 7. U01–U02/F02: постоянный транспорт, компактная навигация, редактор выбора, виртуализация списков и безопасные previews. Проверка XAML/render и размеров окна.
- [x] 8. A01/T01/R01: общий mapper, проверка тестовой инфраструктуры, CI/release script, актуализация документации и итоговый журнал проверок/остаточных ограничений.

Предварительная оценка: сильная основа личного приложения, примерно **6/10 по готовности к широкому использованию**. Тесты и миграции уже существуют и полезны; основной долг — межкомпонентное состояние, восстановление после ошибок и UX, а не отсутствие архитектуры.

## F. Реализация и оценка после исправлений — 2026-09-18

Разделы A–E выше — исходный аудит, не описание уже исправленного кода. Восемь срезов выполнены; оставшаяся часть F02 и дальнейшее дробление MainViewModel сознательно вынесены в ограничения, а не объявлены решёнными.

| D01–D04 | Строгая миграция JSON, дедупликация путей, сохранение повреждённого исходника, безопасная connection string, SQLite backup перед migration, проверка settings |
| S01–S03 | Убран преждевременный LIMIT 500, ограничена длина ввода, сохранены границы слов и стабильный bm25/Id-порядок |

| U01–U02 | Транспорт и действия закреплены; редактор расширен до 360 DIP; компактная шапка/строки, пустая выдача, читаемые состояния выбранного и играющего трека |

Дополнительно обнаружено и исправлено при реализации/проверке:

- **High, WPF binding:** TrackCardTemplate обращался к DataContext ListBox, который после внедрения LeftColumnState не содержит PlayTrackCommand/PlayingTrack/TagsByTrackId. Двойной клик, подсветка и теги теперь привязаны к модели окна. Тест сначала падал на null-команде, затем прошёл для списка, альбома, плейлиста и истории.
- **High, playback:** попытка открыть отсутствующий файл меняла очередь/индекс при продолжающемся прежнем воспроизведении. Валидация выполняется до изменения очереди; три сценария регрессии (next/double-click/album).
- **Medium, audio:** начальная громкость MediaPlayer 0.5 не совпадала с настройками 1.0; NaN доходил до native player; Play без Open сообщал успех. Исправлены defaults, валидация и проверка открытого файла.
- **Medium, metadata:** MusicBrainz неправильно экранировал кавычки и менял параметры общего HttpClient. Теперь экранирует последовательно, использует абсолютный URI и заголовок конкретного запроса.
- **Medium, duration:** m:ss скрывал часы. Общий формат TotalMinutes:ss не обнуляется после 60 минут или суток.
- **Medium, render harness:** закрытие первого окна могло завершать WPF и делать последующие проверки бессодержательными. Также отсутствие Run не запрещало queued OnStartup. Исправлены ShutdownMode, явное отключение production startup, проверки реальной геометрии/команд и timeout.

Проверки перед финальным review: **324/324 теста**, включая benchmark 50k; baseline был 279/279. Release build без предупреждений. NuGet scan, включая транзитивные зависимости: известных уязвимостей не найдено в подключённых источниках на дату проверки. Число тестов не является оценкой полноты покрытия.

### Что ещё ограничивает готовность к публичному релизу

- Не проверены реальный вывод звука/смена устройства, длительный playback soak и upgrade/uninstall в чистой Windows VM. Render 150% — проверка изображения и layout, не полноценный native multi-monitor DPI-тест.
- Загрузка библиотеки, поиск всех кандидатов и группировки остаются синхронными; сетки альбомов не виртуализированы. Убран доказанный N+1 тегов, но benchmark FTS не доказывает плавность всего UI на 50k с большими обложками.
- Только preview импорта ограничивает decode size; общий cover pipeline ещё нуждается в измерении памяти на больших изображениях. Частые изменения громкости всё ещё синхронно сохраняют настройки.
- После независимого review исправлен и финальный commit импорта: окно подтверждения закрывается только после repository.Add. Ошибка БД оставляет кандидата для повтора, отмена удаляет собственные файлы. Аварийное завершение процесса/питания всё ещё может оставить незарегистрированную копию; автоматического удаления неизвестных файлов нет.
- MainViewModel остаётся крупным. Последующее выделение playback orchestration разумно отдельной задачей с текущими тестами, а не как переписывание работающего плеера.
- Версия проекта оставлена 1.0.4, установщик — локальная проверочная сборка текущего дерева. Публикация новой версии, подпись и GitHub release не выполнялись.
