# MusicBakh — стратегический роадмап (2026 → 2029)

Документ фиксирует продуктовое видение MusicBakh, путь от текущего релиза `1.0.0` до версии `3.5.0`, а также «касты» идей, которые сознательно вынесены за пределы основного плана. Адресат — автор проекта; цель — иметь карту местности, чтобы в каждом цикле релизов опираться на единое видение, а не пересобирать приоритеты заново.

Документ описывает **направление**, а не контракт реализации. Конкретные имплементационные планы (`docs/superpowers/specs/...`) пишутся отдельно для каждого минора, опираются на этот файл и могут уточнять детали по факту.

> **Пересмотр 2026-10-15.** Порядок миноров перестроен по зависимостям (доставка обновлений — до крупных фич; форматы — до тегов и лирики; локальные рекомендации — в фазу A; Subsonic — сразу за серверной библиотекой). Ни одна идея не удалена: перенесённые строки помечены `↪`, новые — `🆕`. Соответствие старых и новых номеров — в [разделе 13](#13-журнал-пересмотров).

## 1. Ядро видения

> **MusicBakh = local-first music library + self-host cloud + smart discovery.**

Это якорь продукта. Каждая фича-кандидат проходит через один вопрос: усиливает ли она это ядро или тащит проект в платформенно-операционный хвост (модерация UGC, выплаты артистам, юридические риски hosted-стриминга, ML-инфраструктура big-tech уровня)? Если второе — фича уходит в касту «Возможно потом» или «Не делать соло».

Три равноправных столпа ядра:

1. **Local-first.** Пользователь владеет своими файлами, тегами, плейлистами и историей. Сервер — расширение, а не точка отказа. Десктоп остаётся первоклассным клиентом на всех фазах.
2. **Self-host cloud.** Когда у пользователя появляется потребность в синхронизации, веб-доступе и мобильнике, он поднимает свой сервер (Docker, VPS, домашний NAS) и владеет своим контуром. Hosted-тариф автора — только удобная альтернатива для тех, кто не хочет поднимать инфраструктуру.
3. **Smart discovery.** Рекомендации работают **поверх своей библиотеки** в первую очередь и поверх агрегированной анонимизированной информации сети self-host инстансов — во вторую. Это отличает MusicBakh от «личного Spotify» в позиционировании.

## 2. Версионирование

Используется semver:

- **Мажор** — смена парадигмы: `1.x` = десктоп, `2.x` = десктоп + backend, `3.x` = мультиклиентная социально-AI-обогащённая платформа.
- **Минор** — крупная фича-волна, обычно одна тема на минор (Audio Engine, Metadata, Backend MVP, и т.д.).
- **Патч (третья цифра)** — последовательные итерации внутри одного минора. Каждая итерация выпускается как самостоятельный релиз с инкрементом patch-цифры, чтобы пользователь получал обновления постепенно, а не ждал всей пачки фич минора несколько месяцев. Финальная стабилизация и публикация «готового» минора закрывает последнюю итерацию.

Пример (минор `1.1.0` = «Library 2.0», 8 итераций A–H):

- `1.0.1` — итерация A (чистые слои + SQLite).
- `1.0.2` — итерация B (FTS5 + extended history).
- `1.0.3` — итерация C (рейтинги, лайки, теги-ярлыки).
- `1.0.4` — итерация D (альбомный и исполнительский view).
- `1.0.5` — итерация E (статические плейлисты + технический hardening по аудиту 2026-09-17).
- `1.0.6` — итерация F (умные плейлисты, импорт/экспорт `.m3u8`/`.pls`).
- `1.0.7` — итерация G (ADR модели владения файлами + watched folders).
- `1.0.8` — итерация H (multi-column sort, кастомные колонки).
- `1.1.0` — стабилизация: финальный smoke, доводка перформанса, объявление «Library 2.0» готовой.

Аналогично для `1.2.0` = «Delivery & Foundation» — `1.1.1` … `1.1.k` собирают итерации, потом `1.2.0` объявляется. И так далее по всем минорам фаз A/B/C. В фазе A десять миноров, поэтому последний — `1.10.0` (semver это допускает: минор — число, а не цифра).

Принципы:

- Каждая patch-итерация — рабочий релиз с инсталлятором: пользователь может остановиться на любой и продолжать пользоваться приложением.
- Когда `1.0.x` итерации закончились, минорный бамп до `1.1.0` происходит даже если нет новых фич — это сигнал «эпик закрыт».
- Архитектурные итерации (например, первая в каждом миноре) — допустимы и нужны: они закрывают техдолг, без которого следующая итерация рассыпается.
- Breaking changes публичного API между мажорами анонсируются за минор до выпуска мажора (через депрекацию в `2.x`-релизе перед `3.0.0`).

Условные таймлайны (исходная оценка 2026-05):

- Фаза A (`1.1.0` → `1.9.0`) — 9–12 месяцев соло.
- Фаза B (`2.0.0` → `2.8.0`) — 12–15 месяцев соло.
- Фаза C (`3.0.0` → `3.5.0`) — 10–12 месяцев соло.
- **До `3.5.0` — около 3 лет активной работы.**

**Фактический темп (на 2026-10-15):** `1.0.0` вышел 2026-05-11; за пять месяцев выпущены итерации A–D минора `1.1.0`, итерация E готова к релизу. Это примерно половина первого из десяти миноров фазы A. При сохранении темпа фаза A займёт 2–3 года, а не 9–12 месяцев. Оценки фаз B и C уточняются на ретроспективе после `1.5.0` (см. раздел 12). Документ остаётся картой направления: порядок важнее сроков.

Таймлайн ориентировочный, релизы не привязаны к календарю; цель — корректная последовательность, а не дедлайны.

## 3. Метки идей

В таблицах ниже каждая идея сопровождается тремя метками:

- **Усилия:** `S` = дни, `M` = 1–2 недели, `L` = месяц+, `XL` = многомесячный эпик.
- **Ценность:** `1`–`5` (5 = киллер-фича).
- **Риск:** 🟢 простой / 🟡 нужно подумать / 🔴 экспериментальный или с большим хвостом неизвестных.

Метки субъективные и пересматриваются при планировании конкретного минора.

Пометки происхождения строк (с пересмотра 2026-10-15):

- `🆕` — идея добавлена при пересмотре.
- `↪ из «Тема»` — строка перенесена из другого минора без изменения сути; в исходном миноре на её месте оставлена ссылка `→ «Тема»`. Ссылки идут по названию минора, а не по номеру: номера при пересмотре сдвинулись.
- `✅` — уже сделано (с указанием версии).

## 4. Фаза A — Local-first Windows player (`1.1.0` → `1.10.0`)

### 4.2. `1.2.0` — Delivery & Foundation: installer, updater, crash logs, i18n

Перевод проекта из «exe в релизах GitHub» в «нормально установленное приложение Windows».

**Почему сразу после `1.1.0` (было `1.8.0`):** стратегия частых патч-релизов работает, только если пользователи действительно обновляются. ## 5. Фаза B — Backend + companions (`2.0.0` → `2.8.0`)

Цель фазы: вокруг десктопа появляется опциональный backend, который хранит сетевую часть жизни пользователя (синхронизация, web-доступ, мобильный компаньон, рекомендации) и при этом остаётся self-host'ом первого класса. Hosted-тариф автора — приятное удобство, а не точка отказа.

🆕 **Позиционирование.** Self-host музыкальные серверы уже существуют: Navidrome, Gonic, Jellyfin, Plex/Plexamp, Funkwhale. Соревноваться с ними «ещё одним сервером» бессмысленно. Отличие MusicBakh — **связка**: полноценный local-first десктоп (теги, умные плейлисты, локальные рекомендации, история) плюс сервер, который синхронизирует *эту* жизнь между устройствами и при этом говорит на Subsonic-протоколе. К началу фазы десктоп уже умеет быть Subsonic-клиентом (`1.8.0`), а значит, переход «с Navidrome на свой сервер» для пользователя — смена адреса, а не миграция.

🆕 **Почему такой порядок миноров.** Сначала сервер, который полезен сам по себе: MVP → своя облачная библиотека → Subsonic API. Уже после `2.2.0` пользователь слушает свою коллекцию с телефона через Symfonium или DSub, не дожидаясь собственной мобилки. Двусторонний sync (главный технический риск) идёт следом и проектируется, когда серверная модель данных уже обкатана живыми клиентами. Web PWA и мобилка — после sync, потому что обоим нужны синхронизированные плейлисты, рейтинги и прогресс.

### 5.7. `2.6.0` — Recommendations v1.5: серверная часть

Локальные рекомендации v1 (content-based, Daily Mix, Discover Weekly-аналог, Personal Radio, onboarding) переехали в фазу A — `1.7.0` «Local Discovery». Здесь остаётся то, что без сервера невозможно.

| Идея | Усилия | Ценность | Риск |
|---|---|---|---|

| 🆕 Рекомендации через Subsonic-эндпоинты (`getSimilarSongs2`, `getTopSongs`, радио по исполнителю) — сторонние клиенты получают «умное» радио MusicBakh бесплатно | S | 4 | 🟢 |

**Сознательно не делаем** (перенесено вместе с v1): collaborative filtering между пользователями (нет базы), тяжёлый ML pipeline, обучение моделей на сервере.

### 5.8. `2.7.0` — Scrobble + соц-lite

Социальные функции вводятся минимальным набором: пользователь имеет публичный профиль и может следить за другими, но **без** комментариев, групп, DM и модерации UGC.

| Идея | Усилия | Ценность | Риск |
|---|---|---|---|
| Свой scrobbling-эндпоинт + совместимость с Last.fm API (сторонние клиенты могут слать MusicBakh как Last.fm-сервер) | M | 4 | 🟢 |
| Публичный профиль: топ-треки, исполнители, обложка-коллаж, текущий статус | S | 4 | 🟢 |
| Follow / followers (без ленты, как RSS-подписка) | S | 3 | 🟢 |
| Privacy settings: публичный / только для друзей / приватный профиль | S | 3 | 🟢 |
| Импорт scrobbles из Last.fm / ListenBrainz / Spotify-экспорта | M | 4 | 🟢 |

**Сознательно не делаем:** комменты, группы, DM, ActivityPub-федерация, репорты, бан-система, шейдоу-бан, антифрод-боты. Всё это превращает плеер в социальную платформу с операционным хвостом, который соло-разработчик не утянет.

### 5.9. `2.8.0` — Spotify Connect-style transfer

Передача воспроизведения между **своими** устройствами. Это **не** multi-room: то и другое смешивать нельзя, multi-room — отдельный инженерный зверь с компенсацией latency.

| Идея | Усилия | Ценность | Риск |
|---|---|---|---|
| «Передать на устройство» — продолжить прослушивание на другом своём клиенте | L | 5 | 🟡 |
| Синхронизирующаяся очередь через SignalR / WebSockets | M | 5 | 🟡 |
| «Играть следующим» vs «в конец очереди» — синхронно на всех своих устройствах (локальная очередь → «Audio Engine 2.0») | S | 4 | 🟢 |
| Состояние плеера (позиция, громкость, режим повтора) синхронизируется с задержкой ≤ 1 сек | M | 4 | 🟡 |

**Definition of done фазы B:**
- Self-host инстанс разворачивается одной командой `docker-compose up`.
- Десктоп, web PWA и хотя бы один Subsonic-клиент работают с одним аккаунтом, видят одинаковую библиотеку и плейлисты.
- Sync переживает 24-часовой офлайн без потери данных.
- Recommendations v1 даёт качественный Daily Mix на коллекциях ≥ 1000 треков.

## 6. Фаза C — AI + Reco v2 + Social-lite (`3.0.0` → `3.5.0`)

Цель фазы: добавить социальные элементы и AI-обогащение, оставаясь в рамках того, что соло-разработчик может поддерживать без модерационной команды. AI используется как **усилитель** базовых сценариев, а не как самостоятельный gimmick (никаких TTS-DJ, никаких AI voice clones).

🆕 **Почему AI и Reco v2 идут раньше социалки.** AI-ассистент и рекомендации на эмбеддингах дают ценность одиночному пользователю на его собственной библиотеке и не зависят от сетевого эффекта. Социальные функции, комнаты и лента бессмысленны без активной базы пользователей, поэтому они идут во второй половине фазы, когда база успела вырасти (метрики — раздел 10.8). Мажор `3.0.0` при этом по-прежнему означает «мультиклиентная платформа с AI и социальным слоем» — социальный слой просто приходит в `3.2.0`.

### 6.1. `3.0.0` — AI Assistant over Library

Ставка на **полезный** AI — над библиотекой пользователя, а не как gimmick.

| Идея | Усилия | Ценность | Риск |
|---|---|---|---|
| Промпт-плейлисты: «собери мне 30 треков для долгой ночной поездки по трассе» → LLM матчит на твою библиотеку. Развитие «опиши словами → правило» из `1.7.0`: от фильтра по метаданным — к подбору по контексту, а с эмбеддингами `3.1.0` — и по звучанию | M | 5 | 🟡 |
| «Объясни этот трек» — LLM пишет краткий контекст про артиста, эру, влияние, что слушать после | S | 4 | 🟢 |
| AI mood/situation теги: после прослушивания LLM предлагает теги (можно принять/отклонить) | M | 3 | 🟡 |
| AI-описание исполнителя на твоём языке, если в источниках только английский | S | 3 | 🟢 |
| Голосовые команды: Whisper локально + intent-классификатор для команд «поставь что-нибудь спокойное», «следующий», «лайк» | L | 4 | 🟡 |
| Локальный LLM-агент (опция для тех, кто не хочет слать запросы вовне): Ollama-совместимый интерфейс, llama.cpp под капотом | L | 3 | 🟡 |

**Сознательно не делаем:** AI DJ с TTS-репликами между треками (gimmick), auto-mashup (юр.+качество), AI-кавер голосами артистов (этика+юр.минное поле), AI-генерация обложек для всех треков (низкая ценность). Stems separation (Demucs/Spleeter) — только как локальная экспериментальная фича для караоке-мода, не как самостоятельная фича.

### 6.2. `3.1.0` — Recommendations v2 (embeddings)

Вторая версия рекомендаций, уже на эмбеддингах, но **без** big-tech-усложнений.

| Идея | Усилия | Ценность | Риск |
|---|---|---|---|
| Audio embeddings: CLAP / MERT / OpenL3, треки → вектор 512–1024-d | L | 5 | 🟡 |
| pgvector или Qdrant как векторное хранилище | M | 4 | 🟢 |
| Similar tracks по cosine similarity, доступно в контекстном меню любого трека | S | 4 | 🟢 |
| User embedding как взвешенное среднее истории прослушиваний | M | 4 | 🟡 |
| Объяснимые рекомендации: «рекомендую X, потому что в твоей библиотеке есть Y и Z с похожим звучанием/настроением» | M | 3 | 🟡 |
| Простой reranker (LightGBM/XGBoost) на «доскипает / лайкнет» с пользовательской историей | L | 4 | 🟡 |
| Cold-start: новые пользователи получают рекомендации по своему первому импорту через audio-fingerprint match | M | 4 | 🟢 |

**Сознательно не делаем:** two-tower retrieval (нужна big-tech база пользователей, иначе игрушка), multi-armed bandits на маленьком трафике, обучение моделей с нуля. Используем pre-trained эмбеддинги.

## 7. Каста «Возможно потом» (за пределами `3.5.0`)

Идеи, которые имеет смысл реализовать, но только после того, как ядро стабилизируется и появятся ресурсы (сообщество, контрибуторы, возможно — спонсоринг).

### Архитектурные

- **Plugin loading с marketplace.** Загрузка сторонних DLL с sandbox-изоляцией (AssemblyLoadContext), supply-chain security (sigstore-подписи), code review, версионирование API, каталог, отзывы. После 3.5, когда внутренний provider API стабилизируется минимум на год.
- **Avalonia-миграция** или нативный Linux/macOS клиент. Web PWA до этого момента закрывает большую часть запроса.
- **E2E-encrypted private mode** — опциональный профиль, где метаданные пользователя зашифрованы клиентским ключом, сервер видит только зашифрованные blob'ы. Жертвуем рекомендациями и публичными профилями ради приватности.
- **Real-time multi-room sync** уровня Sonos с latency-compensation между устройствами.

### Аудио и интеграции

- **ASIO / WASAPI Exclusive / DSD / 24/192 Hi-Res / MQA** — если в комьюнити появится спрос аудиофилов. MQA сейчас почти мёртвый, скорее не стоит.
- **Tesla / автомобильные браузерные UI**, Wear OS / watchOS компаньоны.
- **Stems separation** (Demucs/Spleeter) как пользовательская фича для караоке/DJ-сценариев.
- **Chromecast / AirPlay** receivers (через сторонние библиотеки).
- **CD/Vinyl-режимы** в полном объёме: vinyl assistant с распознаванием через микрофон, поддержка USB-DAC с native ASIO.

### Рекомендации и социалка

- **Two-tower retrieval / multi-armed bandits** — когда наберётся реальная база пользователей.
- **ActivityPub-федерация** — R&D-трек, требует решения вопросов модерации между инстансами.
- **Listening Rooms v2** с voice chat (WebRTC) и точным latency-compensation.
- **Time-machine воспроизведение** топ-100 на дату N лет назад (требует исторических чартов).
- **Family sharing** — несколько членов семьи, разные библиотеки, общая подписка.

### Бизнес и экосистема

- **Hosted-тариф автора** с биллингом, лимитами, поддержкой.
- **Sponsor partnerships** с независимыми артистами и лейблами.
- **Localization to 15+ языков** с участием сообщества (Crowdin / Weblate).

## 8. Каста «Не делать соло, точка»

Десять направлений, в которые нельзя уходить даже с AI-агентами, потому что они требуют команды, денег, юристов, модерации, SLA, договоров — а не только написанного кода. Эта каста — карта реальности, чтобы при контрибутор-предложениях «давай добавим X» сразу было видно, что X — это другая компания.

1. **Полноценная социальная сеть вокруг музыки.** Комменты, группы, DM, модерация UGC, антифрод, репорт-система, шейдоу-бан, бан-волны — это операционная нагрузка большой команды.
2. **Hosted public music storage с публичным шарингом полных треков.** DMCA, RIAA-аналоги, юридические риски хранения чужой музыки.
3. **Plugin marketplace с безопасной модерацией стороннего кода.** Supply-chain security — отдельная инженерная специальность.
4. **Artist platform с верификацией, выплатами и контрактами.** Платёжные системы, налоги, антифрод, договоры, аудит. Отдельный бизнес.
5. **Federation как стабильная и поддерживаемая фича.** Совместимость с Mastodon/Pleroma/Misskey, модерация между инстансами, миграция аккаунтов — большой долгий хвост.
6. **Multi-room low-latency playback уровня Sonos.** Latency-compensation между разными устройствами/ОС/наушниками — R&D-направление.
7. **Spotify-уровень рекомендаций.** Production ML-инфраструктура big-tech-уровня требует команды и базы пользователей.
8. **Полный mobile parity на iOS+Android+Auto+CarPlay+Watches.** Это четыре–пять продуктов одновременно с разными платформенными политиками.
9. **Глобальная hosted streaming инфраструктура для бесплатных пользователей.** Storage, CDN, traffic costs, support — деньги и DevOps.
10. **Legal-safe SoundCloud/Spotify-like публичный шаринг чужой музыки.** Юридическая модель индустрии лицензирования.

## 9. Каста «Не делать никогда»

Эти идеи будут возникать (от себя или контрибуторов) — заранее зафиксированный отказ экономит часы обсуждений.

- **NFT / Web3 wallet login / blockchain-привязка покупок.** Рынок мёртв, аудитория токсична, ценность отсутствует.
- **AI voice cloning артистов** («спой как X»). Этическое и юридическое минное поле, репутационный риск.
- **MQA-сертификация.** Технология практически мертва после ухода Tidal на FLAC.
- **VR-клуб** (Quest/SteamVR) с «летающими обложками» — игрушка, не продукт.
- **Audio-watermarking** приватных загрузок. Ломает совместимость, ловится тривиально, бесполезно.
- **Spotify Connect** через reverse-engineered librespot. Юр.минное поле, может прилететь от Spotify.
- **Brain-computer interface** для смены треков «силой мысли». :)

## 10. Сквозные треки

Помимо тематических миноров, есть направления, которые **вшиваются в каждый минор** и не имеют отдельной версии:

### 10.1. Безопасность

- Регулярный аудит зависимостей (Dependabot, GitHub Security Advisories).
- Авторизация и ввод данных проверяются на каждом эндпоинте после `2.0`.
- Шифрование секретов в локальном хранилище десктопа (DPAPI на Windows, keychain на macOS/Linux).
- 2FA (TOTP) и passkeys (WebAuthn) — целятся в минор после `2.0`, не привязаны жёстко.

### 10.2. Производительность

- Бенчмарк-сьют как часть CI: запуск приложения, открытие библиотеки 100k треков, поиск, переключение треков. Перфоманс-бюджет фиксируется в `1.10.0`.
- Профилирование memory/CPU на каждом миноре с большой UI-нагрузкой (`1.5.0`, `1.8.0`), а также при стабилизации `1.1.0`.

### 10.3. Наблюдаемость

- Feature flags (Unleash или собственное минимальное решение) с `2.0.0` — для постепенного раскатывания рисковых фич.

### 10.4. Качество кода

- Roslyn analyzers с уровня warning-as-error.
- Code coverage минимум 60% для Application/Domain слоёв, 40% для Infrastructure.

- Community-translation через Crowdin/Weblate — в касте «Возможно потом».

### 10.7. 🆕 Сохранность данных

Local-first обещает пользователю, что его библиотека в безопасности. Поэтому:

- Перед любой миграцией схемы — согласованная копия БД (с `1.0.5`: `DatabaseMaintenance`, включая WAL). Ни один сбой не ведёт к автоматическому destructive reset.
- Каждая миграция тестируется на реальной SQLite (`MigratedSqliteDbContextFactory`), а перед релизом — на копии БД предыдущей версии.
- Удаление затрагивает только managed-файлы; оригиналы вне библиотеки и общие файлы не трогаются никогда.
- Экспорт всех пользовательских данных в открытых форматах (`.m3u8`, CSV/JSON, полная резервная копия) доступен всегда, начиная с `1.2.0`.
- С фазы B: sync никогда не удаляет данные без tombstone и возможности восстановления.

### 10.8. 🆕 Метрики успеха

Раздел 12 опирается на «реальный пользовательский спрос», а его нужно измерять. Без измерения роадмап — гипотеза автора. Метрики выбраны так, чтобы не противоречить local-first: всё opt-in и без идентификаторов.

- **Фаза A:** число активных установок (opt-in счётчик из `1.2.0`), доля обновившихся на последнюю версию, число внешних (не авторских) issue и звёзд репозитория, доля сессий без падений по присланным crash-логам.
- **Фаза B:** число self-host инстансов (opt-in), подтверждённая совместимость с топ-5 Subsonic-клиентами, число устройств на аккаунт.
- **Фаза C:** доля пользователей, сохранивших хотя бы один AI- или reco-плейлист; для социальных функций — число взаимных подписок.
- **Порог для социальных миноров `3.2.0`+:** если к концу `3.1.0` активная база слишком мала для сетевого эффекта, социальные миноры откладываются, а время идёт в «Возможно потом» по реальному спросу.

## 12. Условия пересмотра

Этот документ — стратегический, но не священный. Поводы для пересмотра:

- **Появление контрибуторов / команды** → можно поднимать вверх касту «Возможно потом».
- **Резкое изменение технологического ландшафта** (например, выпуск зрелого open-source two-tower фреймворка, который снимает риск).
- **Юридические сдвиги** (например, изменение DMCA-аналогов или появление законных схем для hosted-стриминга в РФ).
- **Реальный пользовательский спрос** на фичу из касты «Возможно потом» — критерий: значимое количество запросов в issue tracker.
- **Через каждые 5 миноров** — короткий ретроспектив-пересмотр: что реально получилось, какие оценки сбылись, что переоценено.

Любой пересмотр оформляется через diff к этому файлу с пояснением в commit message, а не «правкой по ходу».
